description: Executa uma tarefa com várias partes móveis usando o fluxo writing-plans + executing-plans do Superpowers, numa branch comum.
---

Para o ticket atual (o de menor número sem a linha `Concluído em`; sem tickets, a spec):

**Retomada.** Se o plano deste ticket já existe com caixas marcadas, o trabalho foi interrompido: entre na branch com `git switch <funcionalidade>`, pule os passos 1 e 2 e continue o passo 3 da primeira caixa aberta. Antes de começar um ticket novo, confira que não há mudanças não comitadas; se houver, pare e pergunte.

1. Rode `/superpowers:writing-plans` para gerar um plano de implementação com passos pequenos e critérios de verificação. Salve o plano em `.scratch/<funcionalidade>/plano.md` ou, com tickets, em `plano-<número do ticket>.md`, para um plano não apagar o outro (a convenção do projeto vale mais que a pasta padrão da skill). **O plano contém só a execução:** ordem das tarefas, arquivos envolvidos e o teste de cada tarefa. Não reescreva requisitos que já estão na spec ou no ticket; cite-os pela referência (ex.: "critério 3 do ticket 02").
   Se o ticket mexe no banco, no login ou no envio e na abertura de arquivos, leia antes `.claude/regras/banco.md` e cite no plano as regras que valem para o ticket. A primeira tarefa do plano é a do banco, nesta ordem: teste de banco em `supabase/tests/` que falha (ex.: usuário anônimo tentando apagar uma linha e sendo recusado); migração criada com `npx supabase migration new`, com a tabela, a RLS e as políticas da seção Modelo de dados; `npm run db:reset` (local) ou `npx supabase db push` (remoto de desenvolvimento, com o vínculo conferido), `npm run test:db` e `npm run db:types`. A interface acessa o banco por funções de acesso, um módulo por tabela (ex.: `src/data/sugestoes.ts`), sempre pelo cliente de `src/lib/supabase.ts`; os componentes de tela usam essas funções simuladas nos testes, e o `npm test` nunca depende do banco ligado. Migração, teste de banco e tipos vão no mesmo commit.
2. **Isolamento: branch comum, sem worktree.** Crie a branch com `git switch -c <funcionalidade>` a partir da branch principal, na pasta principal, e diga ao `executing-plans` que o isolamento já está feito (ele pergunta por worktree). A branch protege a branch principal do mesmo jeito: se algo der errado, o marco e o `/voltar` resolvem. A worktree cria uma segunda cópia do projeto, e isso trouxe problemas em toda execução: a pré-visualização serve a pasta principal e mostra o código antigo, teste e lint contam a cópia em dobro, o `npm install` da cópia falha e remover a pasta falha no Windows. Só rode direto na branch principal se eu disser que o projeto é um protótipo descartável.
3. Rode `/superpowers:executing-plans` para executar o plano em lotes, validando cada etapa antes de avançar para a próxima. Marque as caixas do plano (`- [x]`) conforme cada tarefa termina.
4. Ao terminar, junte a branch à principal (a opção de merge do `finishing-a-development-branch`; sem repositório remoto não há PR; para voltar à principal use `git switch main`, porque a trava bloqueia `git checkout` de nome que ela não reconhece) e apague a branch já integrada com `git branch -d` (d minúsculo; o `-D` é bloqueado pela trava). Se o `-d` recusar, pare e me pergunte.

**Worktree só se eu pedir** para trabalhar em duas coisas ao mesmo tempo. Nesse caso: a pasta `.claude/worktrees/` já fica fora do git, do Vitest e do ESLint pelo `/setup`; o `.npmrc` do projeto vai junto na cópia; para ver a tela da cópia, suba o Vite dela numa porta própria (ex.: 5174) e encerre depois, sem editar o `.claude/launch.json` da pasta principal.

Se alguma dessas skills recusar ser acionada "nos bastidores" (como aconteceu com skills de invocação direta do Matt Pocock), não insista nem simule o fluxo — me devolva o comando pronto para eu rodar manualmente.

**Quando o `/superpowers:executing-plans` terminar de rodar:** depois do passo 4, na branch principal, se a tarefa era um ticket, acrescente ao fim do arquivo dele a linha `Concluído em AAAA-MM-DD (commit <hash do último commit do ticket>)`; se era a spec inteira, acrescente ao fim dela `Implementado em AAAA-MM-DD (commit <hash>)`. Comite. Veja se há tickets pendentes (os sem essa linha) em `.scratch/<funcionalidade>/issues/` (se a pasta não existir, a spec é o único ticket) e, se não houver, se a lista de `.scratch/projeto.md` ainda tem funcionalidades sem spec. Se houver mais tickets pendentes, aponte o próximo. Se este era o último, lembre explicitamente o próximo passo: `/polir` se a funcionalidade mexeu na interface, ou `/ship` se não mexeu, e diga qual funcionalidade da lista vem depois do `/ship`, se houver. Se a tarefa veio do `/demanda` como bug ou ajuste pequeno, o `/ship` só roda nas condições que o `/demanda` lista (dependência, migração, função, login, permissão ou validação de entrada). Peça também o `/cost`, como manda o `CLAUDE.md`. Não deixe a conclusão terminar só no commit, sem essa lembrança.
