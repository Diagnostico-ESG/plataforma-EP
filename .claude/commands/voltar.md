description: Desfaz algo já feito — uma entrega, uma funcionalidade, uma dependência — voltando a um marco ou a um ponto anterior, sem apagar o histórico. Explica o que se perde em cada opção e só age depois da minha confirmação.
---

Com base no que descrevi que quero desfazer, faça o seguinte, sem executar nada antes da minha confirmação:

1. **Verifique se há mudanças não comitadas.** Se houver, pare e me diga quais são, em linguagem simples, e pergunte o que fazer com elas antes de seguir (elas podem se perder na volta).
2. **Liste os pontos de retorno possíveis:** os marcos (`git tag -l "marco/*"`) e as entregas recentes (commits com mensagem), traduzidos para linguagem simples (ex.: "antes do formulário de contato", "depois do polimento de ontem").
3. **Para cada opção, explique o que se perde:** quais funcionalidades, correções ou ajustes deixam de existir se voltarmos até ali. Se a volta desfaz migrações, diga também quais tabelas ou colunas somem e se isso apaga dados, e confira em `supabase/AMBIENTES.md` ("última migração publicada") quais delas já chegaram à produção: essas ficam fora do `git revert` e são desfeitas por migração nova (passo 8).
4. **Recomende uma opção**, com o porquê, e aguarde minha confirmação.

Depois da confirmação:

5. Crie um marco do estado atual (`marco/AAAA-MM-DD-antes-de-voltar`, com `-2`, `-3` se o nome já existir), para que a própria volta também possa ser desfeita.
6. Acrescente ao `desvios.md` da funcionalidade (ou ao `.scratch/backlog.md`, se não houver uma) a linha `Volta iniciada em AAAA-MM-DD, até <ponto>` e comite. Desfaça com `git revert`, que cria um registro novo e preserva o histórico; se o intervalo inclui um commit de merge (o `/executar-complexo` cria um por ticket), reverta o merge com `git revert -m 1 <commit do merge>`. O revert também desfaz o que foi gravado em `.scratch/` no intervalo (specs, tickets, `desvios.md`, `custos.md`, backlog): traga esses registros de volta com `git diff HEAD <marco antes-de-voltar> -- .scratch/ | git apply` e comite, porque eles são o histórico do projeto e a volta só desfaz código. Arquivo de migração já publicada em produção fica como está, mesmo que o commit dele entre na volta: restaure-o logo depois do revert, com `git show <commit anterior ao revert>:<arquivo> > <arquivo>` (pelo Bash), e comite. Se o trabalho a desfazer estiver numa branch ou worktree que ainda não foi integrada à branch principal, descartá-la é uma opção mais simples: explique e pergunte antes (apagar branch com trabalho não integrado é um dos comandos que a trava bloqueia, então esse passo é meu).
7. **Se o problema for uma dependência** (algo quebrou depois de um `npm install`), prefira `git revert` do commit que mudou `package.json` e `package-lock.json`, e rode `npm install` de novo. Se a mudança de dependência veio misturada com outras no mesmo commit, traga os dois arquivos do marco sem usar `checkout` nem `restore` (a trava os bloqueia): `git show <marco>:package.json > package.json` e `git show <marco>:package-lock.json > package-lock.json` (rode pelo Bash; no PowerShell, o `>` muda a codificação do arquivo e o npm deixa de lê-lo), depois `npm install` e um commit com uma mensagem que diga o que foi desfeito.
8. **Se a volta desfaz migrações:** o `git revert` tira o arquivo, e o banco continua como estava. No local, rode `npm run db:reset` e `npm run db:types` para o banco e os tipos acompanharem. No remoto de desenvolvimento (confira antes a linha "vínculo atual" de `AMBIENTES.md`), explique o que precisa ser desfeito no banco e pergunte antes de agir. Se a migração criou bucket ou política de Storage, os arquivos já enviados continuam lá depois do `git revert`; diga isso e pergunte o que fazer com eles antes de agir. Se alguma dessas migrações já foi publicada em produção (ver `supabase/AMBIENTES.md`), o arquivo antigo fica, e desfazer é trabalho novo: escreva o teste de banco que descreve o estado desejado, crie a migração que desfaz a mudança, aplique no desenvolvimento (`db:reset` no local, `db push` no remoto), rode `npm run test:db` e `npm run db:types`, e comite. A publicação dela em produção segue o roteiro "Publicar no banco de produção" do `/ship`, que aceita esta volta no lugar do `/ship` concluído.
9. Rode `npm test`, typecheck e build (e `npm run test:db`, se a volta mexeu no banco) para confirmar que o projeto ficou consistente.
10. Se uma funcionalidade inteira foi desfeita, atualize a spec dela para refletir que não existe mais (e retire as linhas `Entregue em` e `Em revisão desde`, se houver), e acrescente uma entrada datada no `desvios.md` da funcionalidade explicando o que foi desfeito e por quê, fechada com a linha `Volta concluída em AAAA-MM-DD`.

Comandos que apagam histórico ou arquivos (`git reset --hard`, `git clean`, `git push --force`, `git branch -D`, `git tag -d`) não fazem parte deste comando. Se algum parecer necessário, explique o motivo e peça minha aprovação explícita; aprovado, quem roda sou eu.

Ao final, diga em linguagem simples como o projeto ficou e qual é o próximo passo.
